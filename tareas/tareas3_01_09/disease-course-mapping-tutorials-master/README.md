# Repository Structure and Developer Information

This repository contains code to generate both *challenge* and *solutions* notebooks.
The *challenge* notebooks contain the core progression of the challenges with missing code to be filled by the participants.
Those are in particular made to be run on Google Colab like platforms.
The repository also contains *solution* notebooks, which follows the same structure as the *challenge* ones, except that we included solutions for each questions.
Those notebooks are also already executed, so they can be displayed directly from the Gitlab instance.
Both those *challenges* and *solutions* are generated from common source files.

```
.
├── README.md             # this readme...
├── requirements_dev.txt  # specifies the pip requirement files (for development only)
├── release.py            # script to run before pushing changes that generates challenges/ and solutions/
├── documents/            # contains pedagogical documents used throughout the winter school
├── challenges/           # folder generated by the release.py script, contains to-fill notebooks
├── solutions/            # folder generated by the release.py script, contains filled and executed notebooks
└── sources/              # contains the source notebooks, to be modified using jupyter and jupytext, as well as readme files, requirements and data
    ├── README.md         # the read-me files for workshop
    ├── requirements.txt  # the requirements for workshop
    ├── TP1_LMM/
    ├── TP2_leaspy_beginner/
    └── TP3_advanced_leaspy/
```

## Before editing

Start by installing development requirements in your Python virtual environment:
```
pip install -r requirements_dev.txt
```

## Editing the Markdown source notebooks

In order to edit then notebooks, you should only edit the files located in the `sources` folder.
Assuming you followed the above installation procedure, you should have all the needed python package installed.
More precisely, to edit the notebooks, you need to have the `jupytext` package installed.
This package allows to natively edit the `.md` files that encode notebooks in the `sources` folders.

### Jupyter Notebook

You should be able to directly open those `.md` files using Jupyter Notebook: the jupytext extension will create and maintain a `.ipynb` file synced with the corresponding Markdown file when you open it (simply by clicking on the `.md` file).

### Jupyter Lab

With Jupyter Lab, by default clicking on the Markdown file will open it in a text editor, as a regular Markdown file. In order to open it as a notebook, you should right click the `.md` file and follow `Open with -> Notebook`.

You can modify the settings of Jupyter Lab to allow for "single-click" opening of Markdown files as notebooks by following the “*With a click on the text file in JupyterLab*” section located in the [jupytext documentation](https://github.com/mwouts/jupytext#install).

## Specifying the *challenge* and *solution* notebooks

The content of the *challenge* and *solution* notebooks are are distinguished using [cell tags](https://jupyterbook.org/content/metadata.html).
By default the Jupyter interface does not show such tags.
- *In Jupyter Notebook*: to show and edit them you need to set-up your interface as follows using the following menus `View -> Cell Toolbar -> Tags`
- *In Jupyter Lab*: to show and edit them you need to open the `Property Inspector` tab, which is accessible by clicking on the gearwheel icon in the upper-right corner of the interface

Content differentiation is specified using *tag exclusion*.
This means that the *challenge* notebook is generated by exporting all cells that do not have the `solution` tag (and vice-versa for the *solution* notebooks, which filter-out the `challenge` tags).
Working with an “exclusion” pattern prevents from having to tag every cell: since both versions will share the majority of cells, it is easier (and foolproof) to only tag those that we want to exclude.

You can look at the `subversion_config` dictionary in `release.py` to see how this is specified.

## Committing and Pushing changes

Using jupytext allows to commit *readable diffs* for notebooks.
Therefore, once the desired changes have been performed in the *source notebooks*, only add the `.md` files should be added to the index (by default the `.gitignore` file should prevent the inclusion of `.ipynb` files from the source folder to the commit index).

Because we also want to share functional notebooks, we include a script `release.py` that generate the corresponding *solution* and *challenge* notebooks.
Once you have performed the desired changes in the *sources*, you should run the `python release.py` in order to generate the functional notebooks.
Note that since the *solution* notebooks are executed during their generation, the process can take a few minutes.
If the notebook is correctly composed, this should run without raising exceptions.

The generated `challenges` and `solutions` folders can be fully added to the commit index.
Even though the diffs related to those folders will be hard to follow, it should be sufficient to rely on the diffs in the `sources` folder to understand the content of the commit.

For debugging and testing, you can locally edit the `release.py` script to prevent the re-execution of un-modified notebooks (for instance comment the `notebooks_to_process` entries that you are not working on).
This could be enhanced in the future by only running the notebooks out of sync with the git repo, but I have not looked at it at the moment.
